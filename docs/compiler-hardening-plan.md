# Compiler and runtime hardening plan

Status: implementation in progress, 2026-10-31. Phase 1 has an offline build
and CI gate. Effective property composition, semantic ancestry, numeric counts,
predicate name disambiguation, and atomic relationship updates have landed.
The ontology and configuration fronts now share effective property refinement,
Python descriptors, required/default values, choices, and annotation rendering.
Configurations consume versioned compiler symbols without executing dependency
packages; extension exports carry transitive dependency digests and defining
modules. Required/optional policy bindings and a unified support report have
landed. S223/WaTr built-in policy targets use semantic IRIs.
The user has explicitly authorized
breaking changes: prefer the coherent final interfaces over compatibility
wrappers or preservation of the previous generated API.

Still pending: canonical S223/WaTr identity linking with explicit WaTr profile
behavior; the core/backend lifecycle
split; and semantic upgrade reports. The initial source lock intentionally
captures historical closures rather than claiming recovered import boundaries.
Configuration named ports and scalar quantity schemas remain distinct Python
projections. This work does not claim support for arbitrary SHACL constructive
forms; unsupported constraints remain explicit in validation or fail compilation.

## Objective

Make S223/223P and WaTr upgrades reproducible and reviewable. Changes within
the supported ontology/SHACL subset should require updated inputs and
regeneration. Changes outside that subset should produce actionable
diagnostics identifying the source and the required adaptation.

Keep ordinary generated Python classes, the shared runtime, bundled SHACL,
and immutable resolved models. Simplify public imports and authoring syntax
where that improves the design. Document intentional interface changes and
tightened checks that reject previously accepted invalid models.

## Design criterion: deep modules with simple interfaces

Favor modules that own substantial complexity behind a small, coherent
interface. The architectural layers below describe responsibilities, not a
requirement to create a separate public abstraction or file for every stage.

- The compiler owns loading, normalization, linking, adaptation, emission,
  and diagnostic aggregation. Callers request a generated package; they do
  not manually coordinate passes or understand compiler internals.
- Model authors retain the straightforward entity/relationship API and
  `Model.compile()`. They should not select a solver backend, reconcile
  registries, or manage constraint profiles to use S223 and WaTr together.
- Adapters encapsulate ontology-specific knowledge. Keep ordinary adapters
  internal and declarative where possible; expose customization only for a
  concrete extension-author use case.
- Give each invariant one owner. Snapshot lifecycle belongs to core;
  connection semantics belong to the S223 backend; effective constraint
  composition belongs to the shared compiler. Avoid repeating defensive
  interpretation across callers.
- Prefer a few substantial operations and structured results over many
  pass-through methods, flags, callbacks, or framework extension points.
  Keep IR details and dependency bookkeeping private unless a supported
  tooling use case needs them.
- Make correct behavior the default: resolve pinned inputs automatically,
  preserve semantic constraints, and provide useful diagnostics without
  requiring callers to assemble a safe sequence of operations.

For every proposed abstraction, identify the knowledge it hides and the
decisions it removes from callers. Merge or remove abstractions that merely
forward calls or expose implementation stages. Review public signatures and
representative authoring examples alongside correctness tests; a refactor
that requires more caller coordination has not met the design goal.

## Evidence and baseline

The review found three reproducible gaps:

- An inherited `Animal` range narrowed to `Dog` becomes `Animal | Dog`, so
  the subclass accepts values forbidden by its shape.
- Qualified connection-point extraction ignores the property path and uses
  exact Python class names. An unrelated property can become a port
  requirement, while a custom inlet subclass is overlooked.
- S223 and WaTr generate separate Python definitions for 181 shared class
  IRIs. An S223 fan accepts an S223 quantifiable observable property but
  rejects WaTr's definition of the same ontology class.

The review baseline passed 307 tests, Ruff, and type checking. S223 and WaTr
regenerated byte-for-byte from their bundled graphs. This establishes current
behavior, not correctness of every translation or reproducibility of network
source resolution.

## Architectural contract

```text
pinned documents + import manifest + adapter configuration
                         |
              normalize, resolve, and link
                         |
       semantic IR with source provenance and diagnostics
                         |
         Python API and runtime constraint metadata
                         |
        core runtime + shared S223 resolution backend
```

| Layer | Responsibility |
| --- | --- |
| Source loader | Verify hashes, resolve the pinned import graph, distinguish source documents from local additions |
| Shared compiler | Resolve IRI identities, normalize supported constraints, preserve ontology ancestry, derive effective constraints |
| S223/WaTr adapters | Interpret domain vocabulary and register explicit authoring policy |
| Python lowering/emission | Choose Python bases, names, signatures, descriptors, and metadata from the normalized representation |
| Core runtime | Own entities, relations, model state, transactions, snapshots, serialization, and validation orchestration |
| S223 backend | Interpret connection intentions, solve port/media constraints, and materialize domain-specific results |

Every relevant constraint must be faithfully compiled, explicitly retained
for validation, or rejected with a source-linked diagnostic. Validation-only
support is legitimate; silently weakening a constraint that the compiler
claims to enforce is not.

Ontology ancestry and constraints must survive Python MRO repair. Constructor
requirements are an authoring projection, distinct from graph validity:
deferring a cyclic requirement must not erase its semantic minimum count.
Python cannot express every intersection type, so annotations may be a
documented conservative approximation while runtime checks retain the full
supported constraint.

## Implementation sequence

Each phase should land as focused, passing changes. Add regression tests with
their fixes rather than leaving the default suite failing. Regenerate committed
packages through the generator whenever output changes.

### 1. Pin the inputs and establish an offline regeneration gate

Deliverables:

- Record source identity, version, raw content hash, local snapshot path,
  imports, and local additions in a committed manifest. Record the compiler
  and adapter configuration/version used to build each package.
- Pin one compatible S223 source for both S223 and WaTr; pin their QUDT
  dependencies and the separate QUDT catalog explicitly. Diagnose any
  incompatible dependency versions instead of merging them silently.
- Use the existing bundled graphs to capture a reproducible starting point.
  If original document boundaries cannot be recovered, label these as closure
  snapshots rather than claiming unverified upstream provenance.
- Separate explicit source updating from ordinary offline generation. Share
  loader/orchestration code across the generation scripts.
- Regenerate into a temporary directory and compare generated file sets and
  contents in CI. Detect stale generated files as well as changed files;
  preserve handwritten and nested-package files.

Acceptance: a clean checkout can regenerate S223, WaTr, QUDT, and the supplied
domain configurations with source network access disabled and no diff. A
missing or altered source fails with the exact dependency/hash diagnostic.

### 2. Correct constraint composition and establish shared semantic IR

Deliverables:

- Add regression fixtures for inherited range narrowing, multiple constraints
  on one predicate, explicit alternatives, and inherited cardinalities.
- Represent constraint conjunction separately from alternatives. Preserve
  numeric minimum/maximum counts, semantic IRIs, source shapes, and the
  distinction between required values, defaults, and constructor requirements.
- Compute effective constraints once. Derive Python signatures and runtime
  checks from that result; avoid independent inheritance-merging algorithms.
- Preserve RDF parent edges separately from chosen Python bases. Diagnose
  cycles and MRO repairs, and test semantic subtype checks for omitted bases.
- Detect contradictory supported constraints without assuming unrelated RDF
  classes are disjoint. Retain unfamiliar constraints for validation with an
  explicit support status.

Acceptance: the narrowed-range reproduction rejects a plain `Animal` and
accepts `Dog`; genuine alternatives remain alternatives. Supported runtime
checks agree with SHACL on small positive and negative fixtures. Generated
annotations are type-checked, including documented approximation cases.

Dependency: phase 1 supplies stable regeneration inputs. Scope this phase to
the constructs already used by S223, WaTr, and shipped configurations.

### 3. Extract domain adapters and converge the two compiler paths

Deliverables:

- Move S223 vocabulary interpretation into an explicit adapter: connection
  predicates, direction roots, enumeration semantics, inverse declarations,
  and deferred endpoint properties. WaTr extends this adapter with its
  class-valued properties and authoring policy.
- Resolve port constraints by supported predicate IRI and ontology ancestry.
  Support custom point subclasses and prevent unrelated properties from
  being interpreted as connection requirements.
- Route base ontology and configuration front ends through shared constraint
  normalization, symbol resolution, provenance, and diagnostics. Retain
  distinct projections where configurations need named ports or schemas.
- Replace generated-file comments as the only notification of missing overlay
  entries with structured diagnostics. Mark bindings required or optional;
  missing required bindings fail compilation.
- Emit a support report distinguishing constructor/runtime checks, solver
  constraints, and validation-only constraints. Preserve partial boolean
  constraints conservatively; an unknown branch is not automatically true
  or false, particularly under `xone`.

Acceptance: both port reproductions pass. Renaming a Python alias leaves
semantic extraction unchanged. Equivalent direct, `sh:node`, and `sh:and`
formulations normalize identically where supported by both front ends.
Unsupported constructive forms and unresolved bindings have tested diagnostics.

Dependency: phase 2's common representation. Introduce adapter abstractions
only for responsibilities exercised by the existing ontologies. Normal
generation must remain one operation; front ends and adapters are internal
implementation choices, not additional steps for the caller.

### 4. Link imported class identities across S223 and WaTr

Begin with a small prototype and a recorded design decision before migrating
all generated packages. This is the highest semantic integration-risk phase.

Deliverables:

- Export a versioned dependency manifest of semantic symbols and constraints
  so compilation can link against a base without inspecting its private
  runtime registry as the source of truth.
- Prefer reusing canonical S223 classes for unchanged imported terms. Keep
  ontology identity separate from package-specific shape restrictions.
- Prototype a WaTr-specific restriction on an imported S223 term and mixed
  S223/WaTr hydration. Establish how those restrictions apply without mutating
  the shared S223 class or making behavior depend on import order.
- Choose a coherent public import surface without compatibility aliases for
  their own sake. If a constrained Python view is needed, specify its semantic
  identity, typing, registry selection, and validation behavior explicitly.
- Reject incompatible dependency manifests. Remove duplicate imported
  definitions and related fallback logic only after the prototype proves
  linking and profile behavior.

Acceptance: cross-package properties, containment, connections, class-valued
terms, enums, and hydration work in both package import orders. Mixed models
select the applicable shapes deterministically. Update imports, examples, and
positive/negative type-check fixtures to the final interface. The duplicated-class
reproduction becomes a regression test for canonical identity as well as runtime
compatibility (the latter is now covered by semantic ancestry checks).

Dependency: phases 1–3. Do not solve the identity problem merely by allowing
all equal-IRI values through range checks; subtype and profile constraints
must remain enforced.

### 5. Put model lifecycle in core and connection semantics in the backend

Deliverables:

- Introduce a small resolution interface used by `Model.check()` and
  `Model.resolve()`, with a no-connection path for ordinary RDF models and
  the S223 backend shared by S223 and WaTr.
- Move generic snapshot cloning/materialization lifecycle out of
  `solver223.py`. Core owns transaction boundaries, revision tracking,
  cache invalidation, and snapshot immutability.
- Isolate vocabulary-specific traversal, point restoration, and authoring
  operations behind explicit domain capabilities while preserving existing
  convenience methods.
- Remove duplicated interpretation of effective slots and property
  constraints as the compiled metadata becomes authoritative.

Acceptance: toy and Brick models resolve without invoking the S223 planner.
S223/WaTr retain connection selection, ambiguity reporting, explanations,
transaction rollback, cache invalidation, immutable snapshots, and loaded
graph behavior. Backend selection and coordination remain internal; existing
authoring examples need no additional setup. Compare representative connection
workloads against the pre-refactor baseline to catch substantial regressions.

Dependency: phases 3–4 stabilize metadata and registry contracts.

### 6. Make ontology upgrades a tested maintenance workflow

Deliverables:

- Produce a deterministic semantic diff of source/IR versions: added or
  removed terms, ancestry, ranges, cardinalities, defaults, port requirements,
  public names, dependency versions, and constraint support status.
- Add an evolution matrix covering added subclasses, narrowed ranges,
  changed cardinalities, equivalent shape syntax, namespace/name collisions,
  removed adapter targets, and unsupported constructs.
- Keep graph-isomorphism checks for RDF semantics alongside byte comparisons
  for deterministic generated artifacts. Test fresh parses and reordered
  triples rather than relying on one graph's iteration order.
- Exercise positive and negative model validation, serialization/hydration,
  mixed-package usage, and generated typing against the pinned fixtures.
- Document the source-update, semantic-review, regeneration, and verification
  procedure. Update DESIGN.md and compiler documentation to match the final
  implementation rather than retaining conflicting aspirational descriptions.

Acceptance: a maintainer can perform a representative supported ontology
update by changing the manifest/sources and regenerating, with no compiler or
runtime edits. An unsupported change identifies the affected source constraint
and adaptation point. CI checks offline regeneration and semantic regressions.

Dependency: source capture starts in phase 1; evolution fixtures are added
throughout phases 2–5. This phase completes the report and maintainer workflow.

## Verification and scope

For each implementation change, run focused semantic tests, then the repository
checks (`make check`). For generated/public API changes, also run the relevant
example/regeneration checks, documentation checks, and distribution smoke tests.
Document expected generated diffs and any intentional compatibility changes.

This effort does not add a general OWL reasoner, full SHACL-SPARQL-to-Z3
translation, WaterTAP translation, or a general plugin framework. Keep
unsupported SPARQL constraints in authoritative validation and expose their
status. Brick remains a regression target; S223 and WaTr drive the new contracts.

Completion means all three review reproductions are covered, generation is
offline and pinned, compiler front ends share effective constraint semantics,
cross-package identity is coherent, the runtime/backend boundary is explicit,
and an ontology upgrade produces a useful semantic report. Public interfaces
remain small and coherent, with less implementation knowledge required of
callers.
